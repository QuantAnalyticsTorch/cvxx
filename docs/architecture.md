# Architecture Decisions

This document records significant architectural decisions for `cvxx`. Each
entry follows the architect note format; see `docs/architecture/` for none
yet split out as standalone notes.

---
date: 2026-09-30
topic: Adopt clarabel as the standing solver framework
status: accepted
---

## Observation

`ISSUE-0010` / `SPEC-0010` needed to replace `cvxrust::solve`'s permanent
`"not implemented"` stub with a real solver. The initial draft of SPEC-0010
proposed a hand-rolled two-phase simplex implementation living entirely
inside the `cvxrust` placeholder crate, with no new external dependency.

## Recommendation

Use [`clarabel`](https://crates.io/crates/clarabel), a pure-Rust conic
solver, as the numerical engine behind `cvxrust::solve`, rather than
hand-rolling and maintaining a simplex implementation. `clarabel` natively
supports free (unrestricted-sign) variables and both linear and quadratic
programs, so the same `Problem` → conic-program translation layer
(`P`/`q`/`A`/`b`/cones) built for this issue's linear-programming scope is
the intended foundation for quadratic-objective support later, rather than
a second, unrelated solver integration.

`clarabel` is a dependency of `cvxrust` only; `cvxx` continues to depend
solely on `cvxrust`'s existing public API and must never import `clarabel`
directly, preserving the layered boundary in `copilot-instructions.md`
("Optimization layer: `cvxrust` problem formulation and solvers").

## Rationale

- Avoids maintaining bespoke simplex/anti-cycling logic (Bland's rule,
  degenerate pivoting, free-variable splitting) that a real solver already
  handles correctly and efficiently.
- Establishes one solver framework for the whole roadmap (LP now, QP next)
  instead of adopting a different crate per problem class.
- Pure Rust, no C/BLAS/LAPACK toolchain requirement for the cone types this
  project currently needs (`ZeroConeT`, `NonnegativeConeT`), keeping the
  Windows XLL build simple.

## Affected Components

- `specifications/0010-convex-solver-backend.md` (updated to specify
  `clarabel` instead of a hand-rolled simplex).
- `cvxrust/Cargo.toml` (new `clarabel` dependency).
- `cvxrust/src/lib.rs` (`solve` implementation, `Variable` identity fix).
- `.github/copilot-instructions.md`, `.github/agents/cvxx-developer.agent.md`,
  `.github/skills/cvxx-optimization-modeling/SKILL.md`, `README.md` (updated
  to document `clarabel` as the standing solver framework).
- Future specifications extending problem-class support (e.g. quadratic
  objectives) should extend this `clarabel` translation layer rather than
  introduce another solver crate.

date: 2026-10-03
topic: Keep user documentation synchronized with specifications
status: accepted
---

## Observation

The existing CI built the mdBook and checked links, but the public XLL surface
could grow without a corresponding user-facing reference. For example,
`CVX.PARAMETER` was implemented by SPEC-0002 but did not appear in the
documentation function index.

## Recommendation

Treat documentation updates as part of implementing a specification, not as
follow-up work. Each specification should identify affected user-facing pages
and examples, or state why there is no user-visible documentation impact.
Implementations should update those sources in the same change as the behavior.
The Markdown under `docs/` is canonical; `docs/html/` is generated by mdBook.

CI builds the book, checks internal links and rendered pages, and verifies that
every exported `CVX.*` function is mentioned in the Markdown documentation.
That automated check is a coverage guard only: review must still verify the
documented signature, behavior, return value, errors, and examples. Generated
example workbooks should likewise be refreshed and checked when a
specification changes their behavior or coverage.

## Rationale

- Updating user documentation alongside implementation keeps release and
  offline help content aligned with shipped behavior.
- A CI coverage check catches entirely undocumented public Excel functions
  before changes merge.
- Requiring each specification to name its documentation impact makes the
  review obligation explicit even for changes that do not add an XLL function.

## Affected Components

- `.github/copilot-instructions.md` and
  `.github/agents/cvxx-technical-analyst.agent.md` and
  `.github/agents/cvxx-developer.agent.md` (specification and implementation
  expectations).
- `scripts/check-public-functions-documented.ps1` and
  `.github/workflows/ci.yml` (automated API coverage check).
- `docs/README.md`, `docs/SUMMARY.md`, and `docs/parameters.md` (public
  reference for `CVX.PARAMETER`).

topic: Example workbook and documentation color palette
status: accepted
---

## Observation

`SPEC-0017` introduces `tools/gen-examples`, a generator that produces
every `docs/examples/*.xlsx` workbook, replacing the single hand-built
`Introduction.xlsx`. Every generated workbook shares one blue/white visual
theme (`tools/gen-examples/src/theme.rs`'s `Theme` struct) so the set of
workbooks reads as one consistent, branded product.

## Recommendation

Record the six hex colors that make up this palette here, as the one
canonical, cross-referenced source of truth, rather than letting them live
only inside `theme.rs`:

| Element | Hex | Used for |
|---|---|---|
| Dark blue | `#1F4E78` | Workbook title band |
| Mid blue | `#2E74B5` | Column headers; result-cell border |
| Pale blue | `#DCE6F1` | Input (known numeric data) cells |
| Very pale blue | `#EAF1FB` | Result/answer cell fill |
| White | `#FFFFFF` | Narrative prose and formula cells |
| Black | `#000000` | All body text |

A future `mdbook` custom-CSS pass over `docs/html` should reuse this same
palette rather than inventing a second one, so the generated workbooks and
the rendered documentation feel like one product.

## Rationale

- `theme.rs` is implementation, not documentation; a reviewer auditing
  `cvxx`'s visual identity should not need to read Rust source to find the
  palette.
- Keeping one canonical definition avoids the palette silently drifting if
  `docs/html` theming work and `tools/gen-examples` are touched by
  different changes over time.

## Affected Components

- `specifications/0017-autogenerated-branded-example-workbooks.md`.
- `tools/gen-examples/src/theme.rs` (the palette's implementation).
- Future `docs/html` custom-CSS work, if it happens, should cite this
  entry rather than redefine the palette.
